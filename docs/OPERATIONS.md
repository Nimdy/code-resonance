# Operations

Running Code Resonance day to day: where its data lives, how to back it up, update it and roll it back, what the
receiver prints, and what has and has not been verified. Setting it up for the first time: [FIRST-RUN.md](FIRST-RUN.md).

## Status

Product version **0.7.2**. The last published GitHub Release before the 0.7 series is **0.6.0** (`v0.6.0`). For private use on your own machine; it
is not stable. It runs from this repository, or from the VS Code extension alone: the VSIX carries the receiver and the
extension starts it when none is running ([Getting started](FIRST-RUN.md#with-the-extension-alone)). Publishing to the
Visual Studio Marketplace and Open VSX is prepared, not done ([PUBLISHING.md](PUBLISHING.md)). The product version is separate from the versions of
the data formats, the score, the Visual Recipe generator, the interpretation (10) and the Visual Pack SDK
([ARCHITECTURE.md](../ARCHITECTURE.md#versions-and-compatibility)). Overnight CAST and a public OBS night:
[campaign-0.7.md](campaign-0.7.md). The README hero is a 70-second CAST session of Pulse.

## Current limitations

- **Platforms:** only the environments above. Visual pack isolation was probed in Chromium only.
- **Long sessions:** no multi-hour soak has completed with the final code, and no multi-hour real development session
  has been recorded (the longest runs: 110 minutes locally and one hour in CI, both before the flagship worlds).
- **Recording** kept in memory (the default) holds the file in the browser's memory until you stop: about 60 MB a
  minute at 720p and 90 MB at 1080p, so for anything longer than about half an hour choose *Record to a file on disk*
  (Chrome or Edge: written to disk as it records, bounded by disk, kept through a crash; qualified headless only, and
  not with the real Save dialog on Windows) or use OBS. At 1080p the built-in worlds need a capable GPU; on software
  rendering they record at a few frames a second. Details: [RECORDING.md](RECORDING.md).
- **Listening and viewing:** the owner has reviewed the application, its worlds, the digital-life films and the
  creative direction. No one else has, and whether the music stays pleasant through hours of work is not established.
- **Interpretation:** TypeScript and JavaScript are analysed with the TypeScript compiler; Python, Go, Rust, Java,
  Kotlin, C#, Swift, C/C++, PHP and Ruby by dependency-free scanners, which do not see what only a compiler or the
  running program knows (code generated by macros, annotation processors or metaprogramming, routes whose path is not a
  literal, alternatives of conditional compilation that would unbalance braces), and resolve C# namespaces only to
  candidate folders; each adapter's header in `engine/languages/` lists what it does not recognise. Other languages
  count at file level. The scanners ran without errors over the Python 3.12 standard library, part of the JDK 21
  sources and the system's C and C++ headers, and over a handful of real Go, C#, PHP and Ruby files; Rust, Kotlin and
  Swift are verified on fixtures only. Interpretation **10** (language adapters,
  the larger agent catalog) is independent of the product version. AI agents with an observe-only adapter: Claude
  Code, Cursor, Codex, Gemini CLI, Qwen Code, GitHub Copilot (CLI and VS Code's Copilot harness), Factory Droid, Grok
  Build and goose. Any other agent can report only through `scripts/event.js` (why each has no adapter:
  [AGENTS.md](AGENTS.md)). Stage chips show CAST catalog names (Claude, Cursor, Codex, Grok, Qwen, Kimi, Gemini,
  Copilot, Droid, Goose, OpenCode, Cline, Windsurf, Amp, Kiro, Augment, Junie, Aider), not vendor art; any other
  provider is shown as "Agent". Eight seats: later providers share a colour and voice with an earlier one and are told
  apart by their chip.
- **Cursor hooks:** prove only in a trusted workspace; CI does not run Cursor.
- **Codex hooks:** prove only in a trusted workspace (project `.codex/` must be trusted); CI does not run Codex. Paths only from patches; `PreToolUse` is not installed.
- **Gemini CLI, Qwen Code, GitHub Copilot, Factory Droid, Grok Build and goose hooks:** implemented from each tool's
  documentation (checked 2026-10-30) and tested against its documented payloads only; no real session of any of them
  was run, and CI runs none of them. Their payloads document no shell exit codes (commands show a category and at most
  *failed*); Copilot and Grok name no files, Droid only for `Create`. Copilot (and Grok Build, Devin) also read the
  repository's Claude Code hook files: with Claude Code's hooks installed, a Copilot session can also appear as Claude.
- **Labels at the edge:** agent chips and explorer labels stay inside the frame (they flip, then they are omitted). A
  callout that cannot sit near its subject becomes a caption.
- **Three catalogued values have no visible effect on one world each:** *Reactivity* (`music.reactivity`) on Machine
  Cathedral, *Beat pulse* (`music.beatPulse`) and *Blossom scale* (`secondary.blossomScale`) on Fractal Biosphere. The
  Visual Studio and the Music Studio still offer them. They stay in the parameter catalogue so that saved recipes and
  packs that set them remain valid; making them work would change the approved look of those worlds.
- **Digital life:** images are identical across runs only on the same GPU and driver. A replay hands its ecosystem to
  the next generation every 10 minutes, visible as a short breath. Not run on Windows or in OBS.
- **The Music Studio and the Artist Studio** were not run on Windows, macOS or in OBS, nor with a composition through a
  live session longer than a few minutes.
- A replay reconstructs only what was captured after capture began.

## Where data lives

Everything is on the computer that runs the receiver, in its data directory: `~/.code-resonance` by default
(`%USERPROFILE%\.code-resonance` on Windows). `RESONANCE_DATA` or `npm start -- --data <dir>` chooses another one.

| Path in the data directory | What | If you delete it |
|---|---|---|
| `receiver-auth.json` | the ingestion token, the pairing key, the last port (mode 0600 outside Windows) | a new token and key; the extension reconnects, browsers must pair again |
| `settings.json` | global preferences | the defaults |
| `presets.json` | visual and music presets | presets are gone |
| `compositions.json` | the Artist Studio's compositions, each with its last five versions | compositions are gone (a project that applied one keeps its copy in its recipe) |
| `packs/<id>/`, `packs/trust.json` | installed visual packs, digest-bound approvals | packs or approvals are gone |
| `packs/.quarantine/` | imports waiting for review | emptied at every start anyway |
| `projects/<hash>/events.jsonl`, `blobs/` | the journal of observations and the compressed source snapshots: the source of truth | the project's history is gone |
| `projects/<hash>/performance.jsonl`, `state.json`, `public.json` | the recorded timeline and its checkpoints, derived from the journal | rebuilt from the journal |
| `projects/<hash>/evidence.json` | what capture was observed, derived from the journal | rebuilt from the journal |
| `projects/<hash>/recipe.json`, `preferences.json` | the project's visual identity and its own choices | a new identity is generated by today's generator; the global choices apply |
| `projects/<hash>/salt` | the secret behind the project's public ids | ids change; keep it with the journal |
| `spool/` | agent hook events waiting for the receiver | those events are lost |
| `logs/receiver.log`, `receiver.log.1` | the output of the receiver the extension started (two files of at most 5 MB) | nothing; the next start writes a new one |
| `bundled-receiver.json` | the receiver the extension started: process id, port, version, its files, when | the extension no longer knows it started it: it is reused, but *Stop Receiver* will not stop it |
| `bundled-receiver.lock`, `bundled-receiver.stop` | a window starting the receiver; a request to stop it (both short-lived) | nothing (a stale lock is taken over) |
| `hooks/` | the agent hook adapters that hook entries written by the extension's receiver run (a path that survives extension updates), and `manifest.json` (which version wrote them) | those hooks fail until the extension's receiver starts again (it writes them back) |

The VS Code extension reads the token from `~/.code-resonance/receiver-auth.json`, or from `RESONANCE_DATA` when that
variable is set in VS Code's own environment, and starts its receiver with that directory; a receiver started with
another data directory receives nothing from it. Another directory suits the demonstration, tests and the qualification
(`RESONANCE_DATA` applies to `npm run demo`, `doctor`, `pair`, `scripts/pack.js` and every agent hook adapter too).

Outside it: the VS Code extension's outbox (events waiting for the receiver) in VS Code's global storage
(`…/globalStorage/zerobandwidth.code-resonance/outbox`); each browser keeps its pairing key, the active project and a
few interface choices for the receiver's address ([SECURITY.md](../SECURITY.md)). Which setting lives where:
[CONTROL-CENTER.md](CONTROL-CENTER.md#where-configuration-lives), and Settings › Storage & privacy in the Control
Center, which also shows a paired browser this receiver's data directory.

## Recordings, exports and films

- **Record** (kept in memory), the **Audio** (WAV) and **Performance data** (JSON) exports and an Artist Studio
  **Export** (zip) are saved by the browser to its downloads folder; **Record to a file on disk** writes the file you
  chose (its working file stays in the browser's own storage only until it is copied there, or, after a crash, until
  you save or discard it in Record & Broadcast). Code Resonance keeps no copy and no library.
- **Home Last night** is a sped-up replay of a scored highlight window (default 4×; 16× when the window is long),
  chosen from the last 24 hours of the project's recording (the whole history only if nothing there scores). It is
  not a film and does not use Playwright.
- **Films** (`npm run film`, a wrapper around `qualification/visual/film.js`) need a public title, always pass `--copy`
  (so `~/.code-resonance` is not changed), default to cinematic labels, and write
  `qualification/results/films/last-night.webm` unless `--out` says otherwise (never committed), each with the recipe it
  used next to it. Uses the GPU when one is present (`--gpu nvidia` / `--gpu amd` pins an adapter; `--gpu off` is
  software; any other value is refused). A GPU it detected itself that the browser cannot use is reported and the film
  renders in software (slower); a `--gpu` you passed fails instead. The temporary copy (which holds
  `receiver-auth.json`) is removed when the film ends, fails or is stopped with Ctrl-C or SIGTERM. Direct
  `qualification/visual/film.js` still defaults to `qualification/results/visual/`. First time:
  `cd qualification && npm ci`.
- **Record** is live (what the stage shows now, in the browser's memory or written to disk as it records). If you run
  an overnight CAST session, capture lives in the journal; use OBS if you want a live picture of the stage for hours
  (a recording to disk is bounded by disk, but live recordings were measured for minutes only). Last night and `npm run film`
  read the recorded performance, not a WebM from Record.

## Backup

Stop the receiver, then copy the whole data directory. The journal (`events.jsonl`), the snapshots (`blobs/`) and each
project's `salt` are what cannot be recreated; recipes, preferences, settings, presets, compositions, packs and
approvals are your choices. Everything else is rebuilt from the journal. The data directory holds your source
snapshots and the receiver's token: keep the copy as private as the original.

## Receiver lifecycle

`npm start` runs the receiver in the foreground on `127.0.0.1:4174` (`RESONANCE_PORT` or `npm start -- --port <port>`
changes the port); stop it with Ctrl+C. It needs no network and serves only loopback.

**The receiver the extension carries.** When capture starts, or *Open Stage* is chosen, and nothing answers on
`resonance.receiverPort`, the extension starts its receiver: detached, so it outlives the window and VS Code, and
shared by every window through the token proof (two windows starting at once start one). It runs with VS Code's own
runtime from the installed extension's `runtime/` folder; its working directory is the data directory. A receiver that
already answers is always used instead, whoever started it, and the extension never stops one it did not start.
**CR › Receiver status** (or *CODE RESONANCE: Receiver Status*) says which one runs, who started it and since when;
**Stop Receiver** stops the one the extension started (cleanly: the receiver finishes its writes, as with Ctrl+C);
capture or *Open Stage* starts it again. It is not started again on its own: after a reboot, it starts when VS Code
resumes capture or you open the Stage. `resonance.startReceiver` off means the extension never starts one.

While it is stopped, nothing is lost: the extension's outbox keeps events on disk and delivers them when the receiver
returns, and agent hooks keep theirs in `spool/`. After a restart, frames appended after the last checkpoint are
regenerated identically. Pairing survives restarts; capabilities (what a paired browser uses to change things) are
renewed automatically.

## Logs and diagnostics

- **The receiver's output.** `[CODE RESONANCE]` lines at start (address, data directory, a pairing link);
  `[sorter] Rebuilding <id> interpretation vX -> vY` when a project's derived files are rebuilt; `[resonance store]
  <file> is invalid …; using the defaults` when a configuration file cannot be read (the next change saved first copies
  it to `<file>.invalid`, then writes a valid one); `[resonance receiver]` for a failed request.
- **The receiver the extension started** writes the same lines to `logs/receiver.log` in the data directory (never a
  pairing link), plus `[launcher]` lines: the hook adapters it prepared, `started: process …` with its runtime, and
  `stopping (…)` / `stopped`. The **Code Resonance** Output channel in VS Code records each decision (which receiver is
  used, why none was started) and where the log is; *CODE RESONANCE: Show Receiver Log* opens it.
- **`npm run doctor`** checks Node, the receiver, its token and its permissions, projects, packs waiting for approval,
  and WSL2 networking. It is read-only and never prints the token or the pairing key. `--json` for a machine-readable
  report; `--data` and `--port` for another installation.
- **Settings › Diagnostics** in the Control Center shows what this window sees (receiver, browser, world, sound,
  recording) and copies it as JSON without tokens, folders, project names or ids.
- `GET http://127.0.0.1:4174/health` answers `{"ok":true,…}` with the version while the receiver runs.
- `GET /v1/challenge?nonce=&v=2` proves the occupant holds the local token, for the port asked, before any client sends it
  (the extension, `npm run up`, `npm run pair`, the agent hooks, `scripts/event.js`, `npm run demo`). A receiver started
  before this check answers no v2 proof: restart it. Until then the hooks keep their events in `spool/`, the extension in
  its outbox (status *queued (receiver not verified)*), and the commands refuse.

## Updating from an earlier development version

Stop the receiver, update the checkout (`git pull` on `main`), start it again with `npm start`. The application has no
runtime dependencies to install. Rebuild the extension (`npm run package:vsix`) and install the new VSIX over the old
one.

**The extension alone** (a VSIX, or the Marketplace once published): update the extension and reload its windows. A
receiver an older version started keeps running until the next capture or *Open Stage* of the new version, which stops
it and starts its own (a window still on the older version uses the newer receiver rather than replace it). The new
receiver refreshes the hook adapters in `hooks/` in place, so hook entries written before keep working.

On the first start the receiver adapts what it finds, and nothing you made is rewritten:

- A receiver from before 0.5 had no pairing key: one is created, and browsers pair once with the printed link.
- A browser's player choices from before 0.5 move to the receiver once.
- If the interpretation version differs from the one a project was built with, its derived files are rebuilt from the
  journal (the journal itself is never rewritten). Interpretation is **10** (language adapters for Go, Rust, Java,
  Kotlin, C#, Swift, C/C++, PHP and Ruby, deeper Python); that version is independent of the product version. It was 9
  in 0.7.2 (`agent.collision` between catalogued providers, adding no progress), 8 for the CAST catalog in 0.7.0 and
  0.7.1, and 7 from the living worlds until then. Going from 9 to 10 can change the progress and chapter of a project
  with code in those languages: more structure is recognised, and a Python Protocol or ABC now counts as an interface.
  Going from 8 to 9 could lower the chapter of a project on which two agents met, back to what one agent would have
  reached.
- **Identities keep their look and sound.** A project's saved identity keeps the classic score (v2), the Classic finish
  and ecology 1 (or no digital life) until you change them: *Use the composed score* in the Music Studio, *Use the
  Phase 11 finish* (and ecology) and the *Digital life* switch in the Visual Studio. Each is an ordinary tuning you
  can reset.

## Rollback

- **Extension:** install the previous VSIX, or `code --uninstall-extension zerobandwidth.code-resonance`. A receiver the
  newer version started keeps running and the older extension uses it; to run the older receiver, *Stop Receiver*
  first. The hook adapters in `hooks/` are kept at the newer version (an older extension never downgrades them);
  delete `hooks/manifest.json` before starting the older receiver to have it write its own. Uninstalling the extension
  leaves the data directory, a running receiver (stop it first) and agent hooks (remove them first with *CR › Connect
  an AI agent…*, or they keep spooling events to `spool/`).
- **Receiver:** stop it, back up the data directory, check out the earlier version and start it. The journal keeps its
  format, and derived files are rebuilt whenever the interpretation version differs, in either direction. An earlier
  version ignores files it does not know, such as `compositions.json`. Whether an earlier version reads
  recipes and settings written by this one has not been tested: keep the backup until you are sure.
- **Visual packs:** `node scripts/pack.js revoke <id>` or `remove <id>`, or Revoke and Remove in Visual Packs.
- **A look or a composition:** Visual Studio's *Reset customisations*; an Artist Studio composition's **Versions**
  restores one of its last five saves.

## Windows and WSL2

Run the receiver on the same side as the VS Code extension host: inside WSL for a WSL workspace, in Windows for a
Windows folder. The receiver the extension carries starts on that side by itself. A Windows browser reaches a receiver in WSL2 at `http://localhost:4174/` through WSL2's localhost
forwarding, with the receiver still on loopback: [WSL.md](WSL.md). In PowerShell, if npm's script shim is blocked, use
`npm.cmd` (for example `npm.cmd start`). Never set `RESONANCE_ALLOW_REMOTE=1` to make it reachable.
